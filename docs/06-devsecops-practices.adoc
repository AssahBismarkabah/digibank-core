== Part 1: General framework of workshop 3

=== 1.1 General context of the workshop

As part of the UCC152-2 Introduction to Security in DevOps course, Workshop 3 is the logical and direct continuation of Workshop 2, which focused on the static security analysis of the DigiBank project. After examining the source code, identifying the main weaknesses visible upon reviewing the project, and applying an initial set of fixes, it now becomes necessary to examine the application not just as a structured software artifact, but as a real, functioning system exposed to requests, errors, unexpected inputs, and potentially malicious use.
This transition is essential from both a pedagogical and methodological standpoint. An application may indeed appear cleaner after a SAST workshop, successfully compile, pass some of its unit tests, and present a reasonably sound code structure, while still exhibiting problematic behaviors at runtime: overly detailed error messages, insufficient access controls, inconsistent HTTP responses, validations that can still be bypassed via the API, or incomplete session management. Workshop 3 is specifically designed to bring these externally visible weaknesses to light.
=== 1.2 Pedagogical positioning of the workshop

Workshop 3 shifts the student's perspective from that of an internal analyst to that of an external observer. In Workshop 2, the student examined the code, configuration files, dependencies, and certain structural choices to identify weaknesses before execution. In Workshop 3, they must adopt a different approach: they query the application through its actual entry points, analyze the responses returned, observe the behavior of the endpoints, and verify whether the system correctly defends itself against legitimate, invalid, or hostile requests.
This shift in perspective is central to the complementarity between SAST and DAST presented in the course. SAST allows us to identify risk in the code; DAST allows us to observe risk in the application's observable behavior. Students thus learn that robust security cannot rely on a single source of observation. It must be built from complementary perspectives: one focused on the internal structure, the other on the system's actual exposure.

// PDF page 3; printed page 2
=== 1.3 Purpose of workshop 3

The goal of Workshop 3 is to conduct a dynamic security analysis campaign of DigiBank at runtime, and then to correct the vulnerabilities revealed by this external observation. In other words, it's neither about repeating Workshop 2, nor about passively executing a few HTTP calls without any reasoning. It's about designing a true DAST (Dynamic Security Analysis) approach, focused on the detection, qualification, remediation, and revalidation of weaknesses visible at runtime.
The application expected at the end of this workshop should therefore be a version of DigiBank that is not only cleaner in terms of code, but also more robust in its runtime behavior. API responses must be better controlled, unauthorized access scenarios must be properly handled, error messages must avoid unnecessary disclosures, and the management of exchanges with API clients must be more consistent from a security perspective.
=== 1.4 Purpose of workshop 3

This workshop illustrates another fundamental dimension of DevSecOps: security is not built solely through prevention upstream, but also through verification in the execution context. From a purely theoretical standpoint, one might consider that once the code is corrected, security is achieved. However, this course demonstrates that a system must be tested against its real-world behavior, as some weaknesses only become apparent when the application receives requests, generates errors, exchanges session data, or exposes its APIs to an external client.
Workshop 3 thus concretely illustrates the idea that application security must be continuously verified. This logic extends the Shift Left approach without contradicting it. The Shift Left encourages early detection; DAST emphasizes that early prevention must be complemented by runtime validation to prevent seemingly fixed code from still exhibiting risky behaviors once deployed or even simply started in a test environment.

=== 1.5 Why DigiBank is a good support for a DAST workshop

The DigiBank project is a particularly relevant case study for a DAST workshop because it combines several characteristics typical of modern systems exposed to real application risks. It is a digital banking application handling sensitive data, exposing REST endpoints, processing critical operations such as account inquiries, beneficiary management, and transfer execution, all within a modern application service architecture.
**Such an application allows for concrete testing of key aspects of dynamic security:**

the quality of HTTP responses, the robustness of validations, endpoint protection, the consistency of access denials, the behavior of error messages, the control of technical information returned to the client, and, more broadly, the observable robustness of the system in the face of normal or malicious interactions. DigiBank also serves as the central theme of the course, which strongly reinforces the pedagogical continuity between workshops.
=== 1.6 Why DigiBank is a good support for a DAST workshop

In this workshop, dynamic analysis refers to observing DigiBank's security during its actual execution, based on its exposed interfaces and observable behaviors. The focus is no longer on examining what the code appears to do, but on verifying what the application actually does when a client interacts with it.
This analysis involves HTTP calls, targeted test scenarios, valid and invalid requests, observation of status codes, response bodies, error messages, access denials, session behavior, and the effects of certain parameter manipulations. DAST thus seeks to identify external symptoms of security weaknesses, even when these are not immediately apparent from simply reading the code.
=== 1.7 General objective of the workshop

The overall objective of Workshop 3 is to detect, analyze, prioritize, correct, and revalidate security vulnerabilities observed at runtime in the DigiBank application, using a DAST approach consistent with the concepts studied in the course. This objective requires that students be able not only to execute tests, but also to design them intelligently, interpret their results, correct the root causes of the identified anomalies, and demonstrate that the remediation has effectively improved the system's external behavior.

=== 1.9 Scope of the analysis in workshop 3

The scope of this workshop covers vulnerabilities or weaknesses that can reasonably be observed from the outside while DigiBank is running. This includes, in particular, REST endpoints, parameters passed to APIs, responses generated by controllers, behaviors related to errors, validations and unauthorized access, as well as visible symptoms of inadequate session management.
However, the primary objective of this workshop is not to exhaustively analyze dependencies, harden container images, or deeply secure packaging artifacts. These topics are primarily addressed in the subsequent section dedicated to container and dependency security. This distinction is important because it clearly differentiates between the dynamic observation of the system in operation and the analysis of its accompanying artifacts.

=== 1.10 Types of vulnerabilities targeted

Within the DigiBank context, the vulnerabilities or symptoms sought during the
**dynamic analysis may include:**

* Overly detailed error messages returned by the API.
* Responses revealing unnecessary technical information about the environment or implementation.
* Insufficient validations visible from the endpoints.
* Insufficient or circumventable access controls on some roads.
* Imprecise, inconsistent, or incomplete session management.
* Abnormal behavior in response to unexpected, missing, falsified or malicious parameters.
* Inconsistencies between the expected business logic and the behavior observed through the API.

== Part 2: Practical Preparation of DigiBank's DAST Environment

In this second part of Workshop 3, the objective is not yet to immediately delve into the detailed identification of dynamic vulnerabilities, but rather to prepare a sufficiently clean, stable, and reproducible execution and testing environment so that security observations are meaningful. This step is fundamental, because a DAST workshop is not about randomly running a scanner on an application started under uncertain conditions. On the contrary, it is essential to first understand the state of the system under test, know the exposed endpoints, have a usable dataset, and properly instrument the tools that will be used to observe the actual behavior of DigiBank in operation.
This approach is consistent with the course progression. Workshop 1 focused on building a modular, executable, and documented application framework. Workshop 2 then taught participants how to examine this framework from the perspective of its code, dependencies, and static configurations. Workshop 3 naturally extends this work by focusing on the execution level, that is, the observable behavior of the application as it receives HTTP requests, exposes its Swagger documentation, interacts with its database, and responds to normal and abnormal input.

=== 2.1 Role of this phase in the workshop

Before detecting vulnerabilities through dynamic analysis, the student must ensure that DigiBank boots correctly, that the PostgreSQL database is available, that the primary endpoints are responding, and that the testing environment is sufficiently controlled to avoid confusing installation errors with genuine security weaknesses. This requirement is crucial because a poorly prepared DAST often produces misleading results: false negatives if the application doesn't actually function, false positives if certain routes fail for purely technical reasons, or non-reproducible results if the database state changes uncontrollably between runs.
This phase therefore has a threefold purpose. First, it restores DigiBank to a clean, functional state after the corrections made in Workshop 2. Second, it prepares the dynamic testing tools, including the manual HTTP client, the automated scanning tool, and any necessary test scripts. Finally, it establishes the conditions for reproducing the practical exercise, so that two students or two successive runs can observe roughly the same attack surface and interpret the results on a comparable basis.

== Part 3: Detailed Dynamic Analysis of DigiBank, Observation of Real-World Behavior, and Implementation of DAST

=== 3.1 Role of this phase

At this stage of Workshop 3, DigiBank should no longer be approached simply as a project to be read or fixed statically, but as a running application whose observable behavior itself constitutes an object of security analysis. This difference is fundamental. In Workshop 2, the student examined classes, DTOs, services, exceptions, and configuration files to identify structural weaknesses. In Workshop 3, they must now verify how these choices actually translate when an HTTP client interacts with the application, when an invalid request is sent, when an endpoint is explored, or when a dynamic scanner observes the exposed surface.
This section is central to the DAST pedagogical approach. The course emphasizes that certain weaknesses only become apparent at runtime: insufficient server-side

// PDF page 32; printed page 31
validation, overly verbose error messages, exposure of interactive documentation, overly rich JSON responses, or insufficiently hardened HTTP configuration. The goal here is therefore not to abstractly revisit DAST concepts, but to materialize them on DigiBank by demonstrating, for each important functional area, what to observe in the code, what to dynamically verify, which tools to use, and how to interpret the results.
=== 3.2 Expected General Method

As in Part 3 of the SAST Lab 2, students should not simply launch a tool and copy a report. A thorough dynamic analysis relies on a structured sequence. First, it's necessary to start with a properly running application, with an accessible PostgreSQL database and a consistent Spring profile. Next, the code must identify which areas warrant priority dynamic observation. Only then does it become relevant to prepare queries in Postman, execute abnormal scenarios, observe HTTP responses, and then complete the analysis with OWASP ZAP and, finally, with Newman to automate revalidation.
**The logic is therefore as follows:**

* read the code to identify sensitive behaviors that may be visible at runtime;
* launch DigiBank in a stable environment;
* use Swagger to quickly map exposed endpoints;
* use Postman to run precise and reproducible tests;
* use ZAP to observe the attack surface, headers, passive alerts and certain automatically detectable behaviors;
* document the observations in the form of vulnerability reports;
* prepare the remediation in the next section.

== Part 5: Final validation, capitalization of DAST results and preparation for the next stage of the process

=== 5.1 Role of final validation in workshop 3

After the dynamic observation of DigiBank, the execution of DAST scenarios, the interpretation of alerts, and the implementation of remediation measures, Workshop 3 cannot end simply because “the tests seem better.” The DAST methodology, as presented in the course, actually mandates a final validation step, because the objective is not merely to execute simulated attacks or run scanners, but to demonstrate that the exposed application now behaves more securely in real-world situations. In keeping with the learning path, this section therefore plays the same role as the final validation of Workshop 2: it transforms a series of technical actions into a demonstrable, justified, and usable result.
This phase is important for a simple reason. In DAST, a fix is never fully credible until it has been retested externally, under the same observation conditions that revealed the

// PDF page 73; printed page 72
initial weakness. A thorough final validation must therefore demonstrate that DigiBank remains functional, that the previously observed risky behaviors have been reduced or eliminated, that the testing tools no longer detect the same weak signals, and that the evidence produced is sufficiently structured to prepare for subsequent workshops, particularly those focused on dependencies, containers, and security industrialization.
=== 5.2 What needs to be validated after remediation

As with a well-run SAST workshop, the end of a DAST workshop isn't simply about saying a fix has been applied. Several additional dimensions must be verified. The first concerns DigiBank's functional stability. The application must still start cleanly, respond to the main endpoints, accept valid requests, and continue to fulfill normal business use cases. A "hardened" API that has become unusable or inconsistent would not meet the course's pedagogical objective, which is to integrate security without breaking business value.
The second dimension concerns the actual reduction of dynamic signals observed before the fix. If Swagger was freely exposed and is no longer, if overly verbose error messages have been replaced with more concise responses, if server validation now rejects previously accepted abnormal input, or if security headers finally appear in HTTP responses, then the remediation has an observable and verifiable effect. Conversely, if the same behaviors remain visible from Postman or ZAP, then the fix is either incomplete or has not addressed the root cause of the problem.
The third dimension concerns the quality of the evidence. In a DAST workshop, results must be presented in a usable format: screenshots of Swagger and ZAP, Postman exports, Newman outputs, excerpts of before/after HTTP responses, and a reasoned summary linking the dynamic observation to the implemented correction. This requirement is consistent with the DevSecOps approach advocated in the course: security is not a feeling, it is documented, replayed, and demonstrated.

=== 6.2 DevSecOps Logic of the DAST Pipeline

In the context of this course, the CI/CD pipeline is not simply a technical automation mechanism. It constitutes a control center where compilation, testing, quality assurance, dependency management, packaging, and security are integrated into the same workflow. For DAST, this means that dynamic analysis should not be thought of as a random scan run from time to time, but as a set of checks performed at a coherent point in the cycle: after build, after application startup, before wider deployment, or before promotion to a higher environment.
The DAST pipeline must therefore adhere to several principles. First, it must be reproducible: the same version of DigiBank must be tested in the same way each time it is run. Second, it must be targeted: in an educational context, the goal is not to perform a full penetration test with each push, but to replay a core set of high-value scenarios. Finally, it must be interpretable: the results produced must be understandable to the student, with clearly usable reports, test outputs, and artifacts.

=== 6.13 Pipeline Failure Conditions

A DAST pipeline should not fail randomly. What constitutes a failure must be clearly defined.
For the Newman level, the easiest way is to make the job fail if:
* a Postman test fails;
* The application does not start;
* An expected report has not been produced.
For the ZAP level, the approach must be more cautious. In a teaching workshop, it is often
**preferable to:**

* either to publish the report without immediately blocking the pipeline;
* either to block only on certain signals considered critical;
* either to start with an observation mode before introducing a blocking mode.
This gradual approach is consistent with the DevSecOps spirit of the course: integrating security into the pipeline does not mean making it abruptly unusable, but building actionable and proportionate safeguards.

== Part 7: Final validation, capitalization of DAST results and preparation for the next stage of the process

After identifying the dynamic vulnerabilities observable in DigiBank, methodically executing security tests on the live application, and remediating the identified weaknesses, Workshop 3 must conclude with a final validation phase, consolidating evidence and structuredly preparing for the next steps in the DevSecOps process. This last part is essential because a DAST workshop cannot be considered complete simply because alerts were raised by OWASP ZAP, a few requests were modified in Postman, or some application responses were deemed abnormal. It is still necessary to demonstrate that the observed vulnerabilities were correctly interpreted, that the applied fixes effectively reduce the risk without breaking the expected functional behavior, and that DigiBank emerges from this workshop as a more robust, better understood, and better-prepared application for subsequent security audits. This logic is fully consistent with the course, which presents DAST as an analysis of the application's actual behavior at runtime, complementary to SAST and useful for confirming, refining, or revealing weaknesses that only become visible through interaction with requests, sessions, errors, and the system's actual exposure surface. It is also consistent with the DigiBank case study, which emphasizes the need to observe not only the code, but also the APIs, error messages, session mechanisms, access controls, and configurations actually exposed at runtime.
=== 7.1 Role of final validation in workshop 3

The final validation aims to confirm that the work carried out in Workshop 3 was not limited to simple tool exploration or an accumulation of observations, but that it led to a real improvement in DigiBank's dynamic security posture. From a pedagogical perspective, this step is crucial, as it shifts the student from a logic of occasional observation to one of mastery. Running a DAST scan or triggering an HTTP error does not yet constitute securing an application. Securing, within the context of this workshop, means understanding what application behavior reveals, distinguishing truly problematic

// PDF page 104; printed page 103
anomalies from minor side effects, correcting what needs to be corrected, and then verifying that the corrected application remains consistent, stable, and defensible.
This final phase is also crucial because DAST fixes often affect sensitive areas of the system. These can include input validation, HTTP responses, error serialization, token management, protected routes, CORS configuration, cookies, or security headers. A poorly designed fix can make an alert disappear while introducing a functional regression, an API inconsistency, or a new vulnerability. Therefore, in the spirit of DevSecOps, the end of the workshop should not only confirm that a problem has been identified, but that it has been properly addressed, rechecked, and integrated into a continuous improvement process.
=== 7.2 What needs to be rechecked after remediation

Following the remediation phase, several dimensions must be explicitly rechecked. The first concerns DigiBank's functional and technical stability. The application must always start correctly, expose its expected endpoints, handle essential business scenarios, and respond in a manner consistent with legitimate use cases. An application that becomes quieter in terms of error messages but no longer allows for customer creation, account opening, or successful transfer execution would not meet the workshop's objectives. This requirement directly extends the logic of the process, in which security should never be considered as a barrier to the software, but rather as an integral part of its overall quality.
The second dimension concerns the dynamic vulnerabilities themselves. Weaknesses deemed priorities in the previous sections must have disappeared, been mitigated, or clearly defined after remediation. This does not mean requiring a clean OWASP ZAP scan or the absolute absence of any anomalies, as some signals depend on the context, limitations of the test environment, or the depth of the scan. However, truly relevant vulnerabilities, such as an overly revealing error response, insufficient server validation, an accessible critical route without adequate protection, or a missing security header on a sensitive exposure, must no longer exist in their original form. The course specifically reminds us that the DAST is used to observe weaknesses visible at runtime and should be interpreted with discernment, not mechanically reproduced.
The third dimension concerns the quality of security reasoning. In a DevSecOps workshop, remediation is not judged solely on the raw output of the tool. Students must be able to explain why a particular vulnerability was deemed critical, why a specific fix was applied, why a particular behavior was reclassified as a secondary risk, and how the

// PDF page 105; printed page 104
corrected version actually improves DigiBank's security posture. This ability to reason is central to the case study, which emphasizes the need to prioritize risks and build a coherent security response rather than a collection of isolated actions.
=== 7.3 Expected technical checks

Final validation must rely on a clear sequence of technical checks. DigiBank must first be restarted in a clean, stable, and reproducible environment. The endpoints must be retested with standard functional scenarios to ensure that the remediation measures have not broken the expected behavior. This verification can be performed using Postman and, more importantly, Newman, which allows for the systematic replay of the API collection validating the main business cases. This approach is consistent with the logic of reproducibility and automation already present in previous workshops and in the project's industrialization.
Next, the dynamic security tests must be rerun. The same malformed inputs, parameter manipulations, sensitive route tests, HTTP response observations, and ZAP scans must be executed again to compare the state before and after the fix. The goal is not just to confirm a visual improvement, but to have verifiable evidence. If, before the fix, the application returned error messages detailing internal identifiers, accepted unexpected server-side values, exposed insufficient headers, or responded excessively on certain routes, the fixed version should demonstrate a concrete improvement in these same areas.
Finally, this validation must also consider the consistency between DAST and SAST. The course clearly reiterates that SAST and DAST are complementary, one observing the internal structure of the software, the other its external behavior during execution. A vulnerability revealed dynamically must therefore lead to verification that its cause has been corrected in the code, the configuration, or the business logic. In other words, the final phase of workshop 3 is not limited to simply noting that a symptom has disappeared. It must also ensure that the fix implemented in DigiBank is technically sound, maintainable, and compatible with the rest of the course, particularly the workshop dedicated to dependencies, containers, and artifacts.

=== 7.5 Acceptance criteria for a corrected version of DigiBank

A corrected version of DigiBank can be considered acceptable at the end of Workshop 3 if several criteria are met simultaneously. The first criterion is the absence of major functional regressions. Essential business operations must still function correctly. Security must not hinder the service provided by the application, but rather enhance it.

This requirement remains constant throughout the DevSecOps curriculum presented in the course.
The second criterion is the effective reduction of prioritized dynamic vulnerabilities. The anomalies deemed most significant at the time of analysis must have disappeared, been significantly reduced, or be accompanied by a clear technical justification when their correction is not yet fully within the scope of the workshop. A simple cosmetic reformulation without real risk reduction is insufficient. For example, hiding an error message on the front end while maintaining dangerous server-side logic would not constitute satisfactory remediation.
The third criterion is the architectural and operational consistency of the fixes. Remediation must integrate seamlessly with controllers, services, filters, exception handlers, HTTP configurations, and security components. It must not transform DigiBank into an opaque, fragile, or difficult-to-maintain system. This consistency is particularly important in an application like DigiBank, which serves as a guiding principle throughout the course, covering code, execution, dependencies, and deployment.
The fourth criterion is the student's ability to demonstrate the relationship between observation, correction, and result. The workshop aims not only for a technically modified version of DigiBank, but also for a version whose transformations are understood, justified, and traceable. This requirement aligns with the overall spirit of the course, which emphasizes the interpretation of security results and their reasoned integration into a DevSecOps approach.

=== 7.7 What the student should remember from this final phase
