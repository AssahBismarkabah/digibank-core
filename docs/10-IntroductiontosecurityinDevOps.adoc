== Part 1: General framework of workshop 4

=== 1.1 General context of the workshop

As part of the UCC152-2 Introduction to Security in DevOps course, Workshop 4 focuses on container and dependency security within the DigiBank project. Having progressively built, observed, and hardened the application according to the principles already covered, it is now necessary to examine the application not just as code or as a running system, but as a complete software artifact—that is, as a collection of images, third-party libraries, configuration files, build mechanisms, and packaging elements, all of which can potentially introduce vulnerabilities. This transition directly corresponds to Session 4 of the course, which covers risks associated with container images, container security principles, software dependency analysis, identification of known vulnerabilities in libraries, and best practices for updating, reducing the attack surface, and hardening.
This step is crucial because an application can be properly structured, functional, and even tested, yet still be vulnerable due to what it includes during build and execution. An overly large base image, a vulnerable library, a secret left in a configuration, a container running with excessive privileges, or a lack of automated pipeline controls are all enough to severely degrade the system's security posture. Workshop 4 is specifically designed to highlight this often underestimated dimension of modern software risk.
=== 1.2 Pedagogical positioning of the workshop

From a pedagogical standpoint, Workshop 4 shifts the student's perspective on security from a focus on code and application behavior to a broader perspective encompassing delivery and execution artifacts. Previous workshops may have emphasized the quality of the application base, code analysis, or observation of application behavior in operation. Here, the focus shifts to what DigiBank actually imports, builds, packages, exposes, and executes within its technical environment.
This shift in mindset is fundamental to a DevSecOps approach. The course demonstrates that risk doesn't stem solely from the business logic written by the team, but also from third-party dependencies, container images, configurations, secrets, build tools, and the delivery pipeline itself. Therefore, the pedagogical objective of Workshop 4 isn't simply to add another scanner to the project, but to teach students to consider containers

// PDF page 3; printed page 2
and dependencies as objects of analysis in their own right, and then to integrate their control into a continuous security mechanism.
=== 1.3 Purpose of workshop 4

The goal of Workshop 4 is to conduct a security analysis of DigiBank's containers and dependencies, and then to correct the identified weaknesses through remediation, hardening, and automation actions within the CI/CD pipeline. In other words, the expected outcome of this workshop is not a completely new application, but a version of DigiBank with better control over its technical artifacts, a more streamlined package, more secure dependencies, and more rigorous security checks prior to integration or deployment.
It is therefore important to understand that workshop 4 is neither a simple document review nor a superficial demonstration of tools. It is a methodical exercise aimed at identifying at-risk components, understanding why they pose problems in the DigiBank context, proposing corrections consistent with the existing architecture, and then integrating these controls into a CI/CD approach compatible with the principles of the course.
=== 1.4 DevSecOps Workshop Logic

This workshop provides a very concrete illustration of a central idea of DevSecOps: security doesn't stop at the source code or application testing, but must permeate the entire software development chain. In a modern environment, dependencies, base images, container layers, configuration secrets, and build scripts all directly contribute to the system's attack surface. Ignoring them would be tantamount to assuming that software is secure as long as its business logic is correct, a notion explicitly refuted in session 4.
Workshop 4 thus embodies a form of continuity with the Shift Left approach. It's no longer just about shifting the analysis to the code, but also to the packaging and delivery artifacts. Scanning dependencies before release, inspecting Dockerfile build choices, reducing unnecessary components in the final image, avoiding embedded secrets, and crashing the pipeline in case of critical vulnerabilities all stem from this same logic: addressing the risk as early as possible, as close as possible to its point of introduction in the technical chain.

=== 1.5 Why DigiBank is a good platform for a workshop on containers and

dependencies The DigiBank project is a particularly relevant case study for a workshop on container and dependency security, as it embodies several characteristics typical of modern applications. The case study presents DigiBank as a digital banking application built around a web interface, a backend API, a database, application services, and a deployment strategy based on containers and a CI/CD pipeline. This framework provides concrete material for analysis, as it combines business logic, third-party components, configuration, build artifacts, and delivery logic.
DigiBank's value also lies in the fact that the case deliberately incorporates realistic vulnerabilities: legacy dependencies, overly broad base images, secrets still present in certain configurations, incomplete hardening, and insufficient security integration within the automated chain. These elements allow for working on a credible case without resorting to an artificially simplified exercise. In Workshop 4, DigiBank is therefore not simply an application to be run; it serves as a tool for analyzing the risks associated with what a modern application actually incorporates and executes.
=== 1.6 Definition of container and dependency analysis within the workshop

In this workshop, container and dependency analysis refers to the structured examination of external components, libraries, images, build configurations, and deployment artifacts used by DigiBank, with the goal of identifying known vulnerabilities, poor packaging practices, or technical choices that unnecessarily expand the attack surface. This analysis is therefore not limited to verifying that the application builds; it seeks to determine whether what DigiBank imports and executes introduces additional security risks.
This detail is important because an application can be compileable, testable, and even functionally consistent while still carrying vulnerable components or an insufficiently hardened image. The analysis expected in Workshop 4 must therefore cover both declared and transitive software dependencies, files such as the Dockerfile or docker-compose.yml, runtime parameters, the possible presence of secrets in the configuration, and the pipeline's ability to automatically check these elements.

=== 1.7 General objective of the workshop

The overall objective of Workshop 4 is to detect, analyze, prioritize, remediate, and automate security risks related to containers and dependencies in the DigiBank project, building upon the concepts covered in Session 4 of the course and a DevSecOps approach focused on continuous security. This objective requires students to be able not only to run scanning or inspection tools, but also to interpret their results, distinguish truly critical issues, modify the affected artifacts without breaking the project, and then demonstrate that essential controls can be replayed in a CI/CD pipeline.
The workshop is therefore not simply about producing reports. It aims to transform these reports into understanding, and then this understanding into concrete remediation and continuous monitoring. It is in this sense that it fully aligns with the DevSecOps approach presented in the course.
=== 1.8 Specific Objectives

At the end of this workshop, the student should be able to:
* A4.1: Explain the security risks associated with container images and third-party libraries in DigiBank.
* A4.2: Identify the DigiBank files, artifacts and configurations that participate in the containerized construction and execution of the application.
* A4.3: Analyze the project's software dependencies to identify old, sensitive, or vulnerable components.
* A4.4: Examine the Dockerfile, the produced image, and the execution parameters to identify choices that increase the attack surface.
* A4.5: Correct the weaknesses identified through update actions, reduction of attack surface and hardening.
* A4.6: Technically justify the remediations carried out on DigiBank from a security point of view.
* A4.7: Implement a basic CI/CD pipeline to automatically replay the main checks on dependencies and containerized artifacts.
* A4.8: Produce technical deliverables outlining the analysis, corrections made, and evidence of final validation.

=== 1.9 Scope of the analysis in workshop 4

The scope of this workshop covers all weaknesses or vulnerabilities that can reasonably be observed in the dependencies, images, packaging files, runtime configurations, and automation mechanisms associated with DigiBank. This includes, but is not limited to, Maven dependencies, transitive dependencies, pom.xml files, the Dockerfile, any docker-compose.yml files, application configurations that may contain secrets, metadata of the built image, and GitHub Actions workflows related to security controls.
However, the primary objective of this workshop is not to repeat the detailed analysis of the source code or the in-depth observation of the dynamic behavior of endpoints during execution. These aspects fall primarily under the logic already addressed in the other workshops. This delimitation is important because it allows us to clearly distinguish the analysis of build and delivery artifacts from the internal analysis of the code or the external analysis of runtime behavior.
=== 1.10 Types of vulnerabilities targeted

Within the DigiBank framework, the vulnerabilities or weaknesses sought during this workshop may include:
* Outdated or known vulnerable dependencies.
* Basic images that are too wide, too old, or unnecessarily exposed.
* Unnecessary components embedded in the final image, increasing the attack surface.
* Secrets or sensitive settings present in configuration files or versioned artifacts.
* Containers run with excessive privileges or without minimal hardening precautions.
* Ports, files, or execution mechanisms exposed without clear justification.
* A lack of automated control in the pipeline over dependencies and containerization artifacts.
It should be noted that some of these weaknesses do not necessarily imply immediate exploitation, as has already been demonstrated. The workshop's role is precisely to learn to recognize signs of risk before they become more costly incidents to correct, which directly aligns with the continuous safety logic advocated in the course.

== Part 2: Practical preparation of the DigiBank container and

dependency analysis environment
In this second part of Workshop 4, the goal is not yet to immediately delve into the detailed identification of dependency vulnerabilities or the complete hardening of DigiBank containers, but rather to prepare a sufficiently clean, consistent, and reproducible analysis environment so that the security checks performed on the artifacts are meaningful. This step is fundamental because a workshop dedicated to container and dependency security is not about mechanically running a few scan commands on a vaguely open project. On the contrary, it's necessary to start with a functional and already reasonably stable version of DigiBank, verify the build artifacts actually used, check the packaging files, clarify the dependency structure, and put in place the elements that will then allow for credible analysis, reasoned remediation, and realistic automation within the CI/CD pipeline.
This approach is fully consistent with the course progression. Workshop 1 enabled the construction of a modular, executable, and industrializable application base. Workshop 2 taught participants to examine code, configuration, and dependencies from a SAST perspective. Workshop 3 shifted the focus to the actual behavior of the application during execution. Workshop 4 now extends this path by examining the artifacts that truly transport the application into its technical environment: third-party libraries, Docker image, build configuration, injected or embedded secrets, and the future continuous monitoring pipeline.
=== 2.1 Role of this phase in the workshop

Before being able to usefully detect vulnerabilities in dependencies or in the DigiBank image, the student must ensure that the project still rebuilds correctly, that the actual packaging files are present, that the Maven dependency graph is readable, that the Spring configuration is based on appropriate variables, and that the Dockerfile is not simply an artifact that has been forgotten or is inconsistent with the current state of the application. This requirement is important because a security analysis of artifacts quickly becomes misleading if one is working on a partially broken repository, on unused files, or on an image that does not truly correspond to the application being tested.

// PDF page 10; printed page 9
This phase therefore has a threefold purpose. First, it restores DigiBank to a clean technical state before analysis. Finally, it establishes the conditions for workshop reproducibility, so that dependency analyses, image rebuilds, and initial security checks can be consistently replayed, both locally and later in GitHub Actions.

=== 3.2 Expected General Method

In a workshop focused on dependencies and containers, not all weaknesses appear in the same form. Some are directly visible in configuration files or the Dockerfile, others only become apparent when reading the Maven dependency graph, and still others only make sense when the constructed picture is compared to the general principles of attack surface reduction, provenance control, privilege minimization, and control of exposed secrets. The student must therefore learn to identify several complementary families of vulnerabilities, without limiting the analysis to a single type of tool or a single source of information.
The first category concerns vulnerable or outdated software dependencies. The course strongly emphasizes that a modern application executes a significant amount of code that it did not write itself, but rather imported via third-party libraries, frameworks, and components. A vulnerability in a direct or transitive dependency can therefore affect DigiBank without any obvious errors appearing in the local business logic. Identification then involves spotting outdated components, versions known to have public CVEs, and dependency chains that silently inherit these weaknesses.

// PDF page 37; printed page 36
The second category concerns weaknesses in the container's design itself. An image can be functional while remaining unnecessarily large, overly permissive, or too rich in unnecessary components. The course reminds us that the more packages, tools, and layers an image includes, the larger its potential attack surface. In DigiBank, this analysis must therefore focus on the nature of the base image, the distinction between the build and execution phases, the actual content of the final image, port exposure, and how the artifact prepares the service for execution.
The third category concerns the exposure of sensitive information within artifacts or their build context. The risk isn't simply that a password might still be present in a versioned configuration file; it's also the risk that a secret, a local file, a poorly managed variable, or an overly broad build context could end up being carried over into an image, copied into a Docker layer, or propagated through a CI/CD pipeline. This issue is central to Workshop 4, as the course explicitly emphasizes that secrets should not be embedded in images and that containers must remain separate from sensitive data that belongs to the runtime environment.
The fourth category concerns the privileges, permissions, and execution assumptions anticipated by the container. An application running as root, with overly broad permissions, or without preparation for a more restrictive execution mode, presents a higher level of exposure than a service designed with minimal privileges. Here again, the issue is not merely theoretical: if DigiBank were to be compromised at the application level, an overly permissive container would amplify the impact of that compromise. Identifying weaknesses therefore involves not only verifying that the service starts, but understanding the security conditions under which this startup is possible.
Finally, the fifth category concerns the temporal drift of artifacts. A dependency or image that is acceptable at the time of its creation can become problematic over time, as new public vulnerabilities are published. This dimension is pedagogically important because it shows that Workshop 4 does not simply aim for a snapshot of DigiBank, but rather the development of a continuous monitoring reflex. Students must understand that a security artifact is never permanently secure; it must be regularly reviewed, rebuilt, and reassessed.

=== 3.3 Expected analysis method in DigiBank

As in the detailed analysis sections of previous workshops, students should not simply launch a tool and copy what they observe. A thorough analysis of dependencies and containers relies on a structured sequence. First, a cleanly rebuilt project must be started. Next, the files that actually control the packaging and import of third-party components must be examined. Only then does it become relevant to read the reports, observe the resulting picture, and then link the technical signals to clear risk categories.
The expected logic can be summarized as follows:
* review the parent pom.xml and any centralized versions to identify major dependencies and points of attention;
* produce the dependency graph to make visible the direct and transitive components actually embedded;
* launch OWASP Dependency-Check to identify known vulnerabilities reported in libraries;
* Review the Dockerfile, the .dockerignore file, and the docker-compose.yml file to understand the chosen packaging method;
* construct the image, observe its structure, its history, its size and its execution assumptions;
* link each observed signal or weakness to a principle of the course: origin, minimization, reduction of attack surface, control of secrets, reduction of privileges, continuous monitoring.
This method is important because it prevents two common errors. The first would be to assume that a dependency flagged by a tool automatically constitutes a proven exploit, whereas the course emphasizes the need for contextual interpretation. The second would be to assume that a container that starts is automatically a properly secured container. In both cases, the student must learn to move from the raw signal to a reasoned understanding of the risk.
=== 3.4 Practical preparation of the DAST environment

One of the first areas of analysis in DigiBank concerns the Maven dependencies themselves. The Maven parent centralizes a significant portion of the library versions and choices, making it a crucial point of observation in Workshop 4. As the course reminds us, integrating a dependency is tantamount to integrating third-party code, with its

In DigiBank, several categories of weaknesses must be addressed at this level. The first is the use of outdated or poorly maintained versions of core frameworks. When versions locked in the parent pom.xml file are no longer aligned with recent security patches, the application carries a security debt at the very heart of its technical foundation. This situation is particularly critical for core components such as Spring Boot, API exposure libraries, and certain cross-dependencies used across multiple modules.
The second category concerns vulnerable transitive dependencies. In modern projects, the components actually executed are not limited to the libraries explicitly declared by the developer. A direct dependency can introduce several others, which themselves contain still more. DigiBank is no exception to this pattern, and this is precisely why the course emphasizes the need to map the entire software graph and not just skim the pom.xml file. A significant vulnerability can thus stem from an artifact never directly mentioned in the project's code.

An unused or poorly justified dependency nonetheless adds code, sometimes loaded classes, sometimes additional transitive components, and therefore potentially additional CVEs. In the interest of reducing the attack surface, students must learn to consider that an unnecessary library is not simply a matter of technical cleanliness: it is an unjustified increase in the software surface area that needs to be secured.

The course rightly points out that identifying a known vulnerability does not automatically mean that it is exploitable under all conditions. === 3.5 Vulnerabilities searched in the Dockerfile and in the DigiBank image

Beyond Maven dependencies, Workshop 4 requires viewing DigiBank as a containerized project. The Dockerfile should therefore not be considered a simple technical file intended to "make Docker work," but rather a security document in its own right. It specifies the choice of base image, whether or not the build and runtime phases are separated, the files actually copied into the final image, the anticipated runtime environment, and, indirectly, the software surface embedded within the container.
The first potential vulnerability to look for here concerns the origin and nature of the base image. The course emphasizes that an image downloaded from a public registry is not automatically secure simply because it is available, popular, or easy to use. Therefore, in DigiBank, students must consider whether the chosen base image is reasonably maintained, suitable for its intended use, and compatible with a minimization effort. A base image that is too large or too general carries more components, and thus a larger potential attack surface.
The second vulnerability concerns the size and content of the final image. If the Dockerfile doesn't properly distinguish between the build and execution phases, it can include compilation tools, source code, intermediate artifacts, or files in the final image that serve no purpose in the actual DigiBank runtime. This point is central to the course, which presents minimization as a fundamental principle of container security. A lighter image is not only more efficient; it is also more readable, easier to monitor, and less susceptible to the exploitation of unnecessary components.

// PDF page 41; printed page 40
The third vulnerability concerns excessive file copying within the build context or the image itself. A Dockerfile can be functional while still copying the repository too extensively, including reports, local files, technical exports, unnecessary metadata, or configurations not intended for runtime. This problem is particularly significant because it can introduce elements into the Docker layer that should never have left the development machine or the Git repository. Therefore, students must carefully read the COPY instructions, the actual Docker context being used, and check for the possible existence of an insufficient .dockerignore file.
The fourth vulnerability concerns port exposure, launch strategy, and execution assumptions. Exposing a port is not inherently a vulnerability, but it must correspond to a real and well-defined need. Similarly, launching the application with very broad permission assumptions or without preparing for a more restrictive execution is a sign of weakness. The course reminds us here that the container already prepares a behavioral model; it doesn't simply passively wrap the service.
The fifth vulnerability concerns the readability and security maintainability of the Dockerfile itself. A file that is too opaque, too complex, or poorly designed makes future hardening, security reviews, and clean integration into a CI/CD pipeline more difficult. Workshop 4 focuses not only on the image as a final product, but also on the fact that this image must be able to be rebuilt, reviewed, and maintained over time. Therefore, lasting security also requires a minimum level of quality in the packaging structure.

=== 3.6 Vulnerabilities related to secrets and embedded configuration

One of the most important weaknesses to look for in DigiBank at this stage concerns the presence of sensitive information in versioned files, the build context, or the container image. The course explicitly addresses this point, reminding us that a container should not contain passwords, keys, tokens, or confidential configuration files. An image circulates between environments, registries, and actors; any secrets it carries are therefore likely to be disseminated much more widely than intended.
In DigiBank, the first area to examine remains the Spring configuration files. Even if previous workshops have already introduced the logic of environment variables, students must verify that this discipline is indeed followed and that no sensitive identifiers remain hard-coded in an application-dev.yml, a docker-compose.yml, a sample command, a local script, or an export left in the repository. The vulnerability here is not only technical; it is also pedagogical. A bad practice retained in one sample project tends to become a pattern replicated elsewhere.
The second area concerns the Docker context itself. Even if a secret isn't intentionally copied into the final image, it can still be included in the build context if the `.dockerignore` file is missing or poorly designed. This means that an `.env` file, a report, a collection export, internal notes, or other local files can be sent to the Docker engine and then potentially copied into a layer according to the Dockerfile's logic. This situation clearly illustrates how a seemingly peripheral weakness can become a risk of spreading throughout the software build chain.
The third area concerns the environment variables themselves when they are poorly managed. Using environment variables is a significant improvement over hard-coded secrets, but it doesn't absolve the student of the need for security considerations. It's still necessary to verify that sensitive values aren't committed to a versioned local file, that the examples don't normalize bad practices, and that the image build doesn't persistently embed these variables in the Docker layers. Here again, the challenge isn't just to "make DigiBank work," but to ensure that the way it works remains compatible with a credible security chain.
This part of the analysis can usefully be supported by a cross-review of:

The expected outcome is that the student will be able to explain where a secret could still leak, how it could become entangled in an artifact, and why this exposure greatly increases the risk once the image is copied, stored or shared.
=== 3.7 Vulnerabilities related to container privileges and attack surface

Another significant vulnerability in DigiBank concerns container privileges and attack surface. The course emphasizes that a container should not run the application with more privileges than necessary, and that an image must be designed to limit opportunities for abuse, exploration, or privilege escalation. This issue is not simply an abstract "production" best practice; it directly impacts how the artifact is built from the earliest iterations of the project.
The first typical weakness to look for is implicit execution as root. Many images run in this mode by default, which simplifies startup but creates a much more permissive environment than it should be. In DigiBank, even though the project remains educational, students must learn to consider this situation a genuine sign of weakness. Compromising the application in an overly permissive container opens up a more favorable environment for an attacker than running it as an unprivileged user.
The second weakness concerns broad permissions on the container's files or working system. If the application can write too freely, modify areas that don't need to be modified, or run without a clear separation between the application artifact and the environment, future hardening becomes more difficult. The course rightly emphasizes that a secure container is not simply an application package; it is a component designed to reduce the potential for abuse and facilitate control mechanisms.
The third weakness concerns unnecessary components that are still present in the runtime image. An excessively large image may contain shells, diagnostic tools, additional libraries, or other packages that increase the attack surface without being required by the DigiBank service. This situation must be addressed in Workshop 4, as it concretely illustrates the attack surface reduction principle studied in the course.

// PDF page 44; printed page 43
The fourth weakness concerns the implicit dependence on a very permissive environment. A container that only functions correctly because it benefits from broad privileges, ubiquitous files, widely exposed ports, or a very comfortable context is a container that is more difficult to secure in the long term. Students must therefore learn to identify not only explicit weaknesses, but also the assumptions of convenience that mask poor design restraint.

=== 6.4 Criteria for accepting a corrected version

A corrected version of DigiBank can be considered acceptable at the end of the workshop if several criteria are met simultaneously. The first criterion is the absence of major technical regressions. The application must still build correctly, its components must remain consistent, and any modifications introduced for security reasons must not have degraded the overall functionality of the project.
The second criterion is the effective reduction of priority risks. Dependencies deemed problematic must have been addressed, major containerization flaws must have been corrected or mitigated, and the pipeline must now incorporate controls that make these elements visible with each significant change. The course emphasizes that the security of containers and dependencies must be monitored over time, as these artifacts evolve and can become risky again if no continuous verification mechanism is in place.
The third criterion is the architectural and operational consistency of the remediation measures. Corrections must not create new debt under the pretext of reducing existing debt. A good remediation is therefore not only effective; it is also readable, maintainable, compatible with the project, and integrable into its workflow.

=== 6.5 Capitalization of Results

The workshop's conclusion must also explicitly include a knowledge-sharing component. In a DevSecOps approach, it's not enough to simply fix things; a clear record of what was observed, what was decided, what was modified, and what might require further monitoring is essential. Workshop 2 already emphasized the importance of Git, Maven, and GitHub Actions as tools for traceability and reproducibility; this logic remains fully valid here.
This knowledge capitalization can take several complementary forms. First, commits should reflect understandable intentions, such as a dependency update, a Dockerfile hardening, or the addition of a CI/CD check. Second, reports generated by Dependency-Check and pipeline-related artifacts should be retained as evidence of the achieved state. Finally, the workshop report itself should explain the initial problems, the chosen remediations, the results after correction, and any remaining limitations.
From a pedagogical standpoint, this capitalization has significant value. It helps students shift from a tool-execution mindset to a structured analytical approach. It also demonstrates that safety is not just about instant diagnosis, but also about technical documentation, justification, and continuous improvement. A project that properly capitalizes on its remediation becomes easier to revisit, audit, and adapt in subsequent workshops.
