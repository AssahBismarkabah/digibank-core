== Workshop Context

This report documents the runtime security validation required by
`work1-devsecops-practices.adoc`. Static analysis examines source code and
configuration before execution. DAST complements it by sending requests to a
running DigiBank system and evaluating the externally observable responses.

The system under test is the microservices implementation. The API Gateway is
the external entry point; customer, account, transaction and compliance
services remain internal Compose services.

== Test Environment

The validation uses Java 21, Spring Boot 4.1.0, Maven, Docker Compose and
PostgreSQL. The local gateway is available at `http://127.0.0.1:8080`.

Public endpoints are `/` and `/actuator/health`. Business endpoints require
HTTP Basic authentication at the gateway:

* `USER`: normal banking API access.
* `ADMIN`: normal banking access plus compliance and notification access.

Passwords are supplied through `GATEWAY_USER_PASSWORD` and
`GATEWAY_ADMIN_PASSWORD`. The repository defaults are for local education only.

== DAST Method

. Preserve a pre-remediation Newman and ZAP baseline.
. Build the application and images.
. Start the Compose stack and verify readiness.
. Replay functional and security collections with Newman.
. Run the OWASP ZAP baseline scan against the gateway.
. Analyze the externally visible findings.
. Apply gateway authentication, authorization and response hardening.
. Replay the same collections.
. Compare the baseline and remediated reports.

The reproducible command sequence is:

[source,shell]
----
make clean
make build
make image-build
make up
make smoke
make validate-stack
make newman-scan
make zap-scan
----

== Baseline Findings

The pre-remediation reports are stored under `dast/reports/baseline/`.

The baseline campaign is used to record the actual behavior before security
enforcement. Findings are categorized as functional behavior, security
behavior, scanner observations, or accepted educational limitations.


== Workshop 2 Static Analysis Continuation

Workshop 2 extends this security work from runtime observation to static analysis.
The purpose is to inspect the source code, configuration, dependencies and test
strength before the application is executed. This is the Shift Left step: risks
are identified close to the point where they are introduced, then corrected and
rechecked before the runtime validation from Workshop 1.

=== Static analysis scope

The current Spring Boot microservices implementation is the system under review.
The analysis covers the API Gateway, business services, platform services,
Maven dependencies, application configuration, Docker and Compose files, REST
controllers, DTO validation, exception handling, inter-service calls and tests
around security-sensitive behavior. The workshop document refers to the earlier
Java 17 modular-monolith version; this implementation uses the current Java 21
microservices parent and its eight Maven modules.

=== Reproducible commands

The repository exposes the static checks through the root Makefile:

[source,shell]
----
make build
make sast-dependency-check
make sast-pitest
make sast
make sast-sonar
----

`make sast-dependency-check` generates the OWASP Dependency-Check report.
`make sast-pitest` generates mutation-testing reports. `make sast-sonar` sends
the project to a reachable SonarQube server and requires a token. The combined
`make sast` command runs the local Dependency-Check and PITest controls.

=== Local SonarQube configuration

SonarQube is not required for ordinary local builds. It is required locally only
when a SonarQube server is running and a local dashboard is needed. In that case
set the values in the shell, not in a committed file:

[source,shell]
----
export SONAR_HOST_URL=http://localhost:9000
export SONAR_ORGANIZATION=<sonarcloud-organization>
export SONAR_PROJECT_KEY=<sonarcloud-project-key>
export SONAR_TOKEN=<local-sonarqube-token>
make sast-sonar
----

The token must remain outside Git. The GitHub Actions SonarCloud job supplies
`SONAR_HOST_URL`, `SONAR_ORGANIZATION`, `SONAR_PROJECT_KEY` and `SONAR_TOKEN`
through repository secrets and runs the same Maven analysis used locally.

=== SonarCloud finding decisions

The updated SonarCloud dashboard reports a passed quality gate, 33.2% overall
coverage, 2.8% duplication and 30 open issues. Two security issues are visible
in the security snapshot:

* The High CSRF finding is an intentional configuration decision for this
  workshop API. The gateway uses HTTP Basic authentication, has a stateless
  session policy and does not create browser sessions or authentication
  cookies. CSRF protection is designed for browser credentials automatically
  attached to stateful sessions; the Newman session-behavior checks verify the
  selected stateless model. This remains an accepted, documented limitation
  rather than an unreviewed finding.
* The Medium URL-construction finding is treated as a real issue. Gateway path
  variables are now encoded with `UriUtils.encodePathSegment` before they are
  forwarded to downstream services. This prevents path-variable contents from
  changing the downstream request path while preserving the existing API
  routes.

The remaining pasted findings are informational timestamp observations. They
identify uses of `LocalDateTime.now()` in account and compliance error models
and in the gateway exception handler. They do not expose secrets, alter
authorization, or create an injection path. They are retained as a consistency
and maintainability follow-up: if timestamps become part of a cross-service
contract, they should be standardized on an explicit UTC `Clock` or `Instant`.
They are not treated as Workshop 2 security remediations.

The SonarCloud screenshots in
`docs/devsecops/presentation/assets/screenshots/` provide the dashboard and
open-issues evidence. The URL-construction finding was remediated with encoded
gateway path segments and the updated analysis was completed successfully.

== Remediation

The API Gateway now uses stateless Spring Security HTTP Basic authentication.
Business routes require `USER` or `ADMIN`; compliance and notification routes
require `ADMIN`. Health and root endpoints remain public for orchestration and
readiness checks.

The gateway also adds `X-Content-Type-Options`, `X-Frame-Options`,
`Cross-Origin-Resource-Policy`, and no-store cache directives for API
responses. Existing generic error handling and malformed-request handling are
retained and exercised through the security collection.

The authentication model is intentionally suitable for a local workshop. It
does not represent a production identity provider, OAuth2 deployment, or TLS
termination strategy.

== Revalidation

== Workshop 3 Runtime Validation Continuation

Workshop 3 validates the security improvements against the running
microservices system. The purpose is to confirm that the controls identified
through the earlier Newman and ZAP observations remain effective after the
application is rebuilt and started through Docker Compose.

Workshop 2 and Workshop 3 answer different questions. Workshop 2 asks,
"What weaknesses can we identify in the source, dependencies, configuration
and test suite before execution?" Workshop 3 asks, "After those findings are
fixed, what can an external client actually observe when the application is
running?" This second question is necessary because a source-level correction
can still be incorrectly wired, applied only to one route, break a valid
business flow or behave differently after deployment.

The Workshop 3 validation is therefore a post-remediation check, not an
unrelated scan and not a repetition of static analysis. It uses the same
gateway boundary and the same security expectations to demonstrate that the
fixes from Workshop 2 and the earlier runtime remediation are effective in
the deployed Compose topology.

=== Runtime validation sequence

The validation starts with a clean build and a ready runtime. Smoke checks
confirm that the gateway, business services and platform services are
available. The Postman collections then exercise the system as an external
client would: normal requests, missing or invalid credentials, insufficient
roles, malformed data, invalid identifiers and unknown resources. Newman
repeats these checks from the command line, while ZAP provides an independent
scan of the gateway surface.

=== Findings carried into runtime validation

The earlier security work addressed unauthenticated business routes, missing
role separation, overly detailed error paths, incomplete response headers and
missing explicit cache controls for sensitive API responses. The fixes are
enforced at the gateway, where the external API boundary is visible, while
the internal service topology remains unchanged.

=== Post-remediation observations

The current rebuilt stack demonstrates the expected behavior:

* missing or invalid credentials receive `401 Unauthorized`;
* an authenticated `USER` receives `403 Forbidden` for the protected
  compliance route;
* an authenticated `ADMIN` can access the permitted administrative route;
* malformed JSON and invalid requests return controlled `4xx` responses;
* unknown resources do not return stack traces, SQL details, Java class names
  or internal paths;
* authenticated API responses include the expected security and cache headers;
  and
* the stateless gateway does not create a session cookie.

== Functional Regression

Security enforcement must not break normal DigiBank behavior. The validation
therefore retains checks for customer, account, transaction and compliance
flows, gateway routing, public health checks, and complete Compose readiness.

== CI Evidence

The GitHub Actions workflow executes build and tests first, then image build,
Compose startup, smoke checks and stack validation. The Newman job runs after
that readiness gate. The ZAP job runs after Newman. Newman and ZAP reports are
uploaded as independent artifacts, including when a job fails.

Newman authentication and authorization failures are blocking. ZAP low-risk
and informational findings remain visible in artifacts while they are reviewed
and assigned an explicit remediation decision.

== Accepted Risks And Limitations

* The workshop uses a single-host Docker Compose deployment.
* HTTP Basic Auth is a local educational security model.
* Authentication is stateless and does not create server sessions.
* There is no production identity provider or OAuth2/OIDC integration.
* Local validation does not provide production TLS termination.
* Default local passwords must be replaced through environment variables in a
  real deployment.
* ZAP reports a Medium local-only warning because HTTP Basic Auth is exercised
  over plain HTTP; this is not acceptable for production traffic and is why the
  workshop scope is explicitly local.
* Informational cacheability observations for public static resources remain
  visible in the report and are not treated as sensitive API data.
