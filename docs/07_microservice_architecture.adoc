== Part I: Implementation of the Microservices Architecture

=== Context

In workshop 3, students built a first usable version of Digi Bank as a modular monolith using Spring Boot, PostgreSQL, Maven, a WAR package, and deployment on WildFly. This achievement allowed them to stabilize the business scope of the core project, validate the main entities, expose REST endpoints, implement unit tests, and prepare a coherent technical foundation for future architectural evolution.
This workshop proposes a transition to a microservices architecture. The goal is no longer to group all functions into a single application deployed as a single unit, but to distribute business responsibilities across several autonomous services, each responsible for a specific area of the banking system. This evolution addresses concrete needs for availability, independent deployment, resilience, scalability, and more granular maintenance.
Digi Bank retains the same core functionality: customer management, account management, transaction management, compliance monitoring, notifications, and application entry point. However, execution now relies on a constellation of distinct Spring Boot services, orchestrated with Docker, managed by GitHub Actions, and structured according to the microservices principles covered in the course. The project remains intentionally educational: it demonstrates the fundamentals of a distributed architecture without veering into excessive industrial complexity.
=== Scenario

Digi Bank's technical team wants to evolve the platform towards a more flexible and modern architecture. The modular monolith implemented in previous workshops validated the domain, but it shows its limitations when it comes to independently deploying certain functions, isolating faults, or upgrading a module without redeploying the entire system.

// PDF page 3; printed page 2
In this new context, developers must break down the application into separate services, expose consistent REST APIs, organize inter-service communication, manage the persistence of each service, and prepare a reproducible containerized deployment. Your role is to produce a first stable, readable, and directly usable technical version of Digi Bank as a microservice, with a documented, phased implementation strategy.

=== Workshop pedagogy

The workshop follows a progressive structure. It begins with environment preparation, then defines the functional breakdown, before creating the core services, adding orchestration, and finally preparing for containerization and automation. This progression allows students to understand that microservices architecture is not just a technical choice, but a way to organize the system around independent business responsibilities.
In the case of Digi Bank, this approach is particularly interesting because it allows us to illustrate the real tensions of a distributed banking system: coordination of operations, data consistency, fault tolerance, isolation of critical functionalities and supervision of exchanges.

// PDF page 5; printed page 4
=== Target architecture

**The target architecture is based on the following components:**

* API gateway: single entry point for the application
* customer service: customer management
* account-service: account management
* Transaction service: financial operations management
* compliance service: compliance rules
* notification service: business or technical notifications
* discovery-server: service discovery
* config-server : externalized configuration
* a PostgreSQL database per service
* Docker Compose orchestration
* a GitHub Actions pipeline for building and validation.
The logic of the system remains simple to read: the client calls the gateway, the gateway forwards the request to the correct service, each service communicates with its own database, and critical services communicate with each other via explicit calls or appropriate coordination mechanisms.
=== Functional view

**Digi Bank should allow us to illustrate the following functionalities:**

* Customer creation and consultation;
* Account creation and consultation;
* Execution and consultation of transactions;
* Compliance validation prior to processing;
* Sending notifications after sensitive operations;
* Unified access via the Gateway API;
* Supervision of distributed behavior across the studied patterns.

The first conceptual task is to transform the banking sector into independent services. In Digi Bank, the separation of components is avoided by mere technical chance: each service must correspond to an identifiable business capability.
=== 3.1 Services retained

* customer service: customer management
* account-service: account management

=== 3.2 Business logic of each service

* The customer service department manages identity and contact information.
* The account-service handles bank accounts and their status.
* The transaction service applies the financial operations and orchestrates the necessary validations.
* The compliance service verifies regulatory or internal rules.
* The notification service distributes messages related to validated or rejected operations.

=== 14. API Gateway

Without the API Gateway, the client must know and call each service directly. In Digi Bank, this means multiple ports, URLs, and entry points to maintain, complicating testing, security, and system evolution. The problem is even more pronounced when the frontend, Postman, or another consumer needs to communicate with customer-service, account-service, transaction-service, and compliance-service separately.
The API Gateway provides a single point of entry. It receives all external requests, routes them to the correct service, and can apply cross-functional processes such as authentication, logging, and rate limiting. In Digi Bank, it simplifies access to the architecture and hides internal complexity.
=== 14.1 Job Role

The API Gateway receives requests from the client and then redirects them to the relevant service. It can also apply cross-functional filters, such as authentication, rate limiting, logging, or request transformation. This avoids duplicating these processes in each business service.

=== 15. Discovery Service

Without Service Discovery, each service must know the exact address of the others. In Digi Bank, transaction-service could call compliance-service via a hard-coded URL. If the service changes ports or is restarted in a different container, the call becomes unreliable. This is a classic breaking point when moving to a distributed architecture.
Service Discovery solves this problem by introducing a registry where services register dynamically. Calls are made by logical name rather than physical address. This makes the architecture more flexible and more compatible with Docker deployments.

// PDF page 65; printed page 64
=== 15.1 Job Role

In Digi Bank, the transaction service can call the compliance service , and then the notification service . With Service Discovery , it doesn't need to encode static URLs. It simply requests the service by name, and the registry provides the active address. This makes the system more flexible and better suited to container deployments.

=== 18. SAGA (Distributed Operations)

Without SAGA , a distributed transaction may only partially succeed. In Digi Bank, a transfer can debit an account, then fail to record the transaction or send a notification. This results in an inconsistent state, which is unacceptable in a banking system.

// PDF page 79; printed page 78

=== 19. CQRS (Command Query Responsibility Segregation)

Without CQRS , Digi Bank often uses the same model for both reading and writing. This becomes cumbersome as soon as a view becomes complex, such as a customer's complete history, activity aggregates, or dashboards. While write operations need to remain simple, read operations can have very different requirements.
CQRS separates the command model from the reading model. This allows each side to be optimized for its actual use. In Digi Bank, this is useful for transaction history screens or account summary views.
