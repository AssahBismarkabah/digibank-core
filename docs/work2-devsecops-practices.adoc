== Part 1: General framework of workshop 2

=== 1.1 General context of the workshop

As part of the UCC152-2 Introduction to Security in DevOps course, Workshop 2 is the first step explicitly dedicated to the security analysis of the DigiBank application. After designing and implementing a first functional, modular, testable, and industrializable version of the system in Workshop 1, it is now possible to examine this foundation not only from the perspective of its operation, but also from that of its robustness against vulnerabilities present in the source code and in certain associated configurations.
This transition is important because it embodies a fundamental principle of DevSecOps: software must not only be able to execute its functionalities correctly, but it must also be built in such a way as to limit the introduction of exploitable vulnerabilities from the outset. From this perspective, the purpose of Workshop 2 is not to rebuild DigiBank, but to use the previously produced version as material for analysis, diagnosis, and remediation.
This workshop is a direct continuation of the Shift Left principle studied in the course. If security is to be considered as early as possible, then the source code itself must become a primary object of observation. This is precisely the role of SAST, or static security analysis, which allows for the examination of code even before the application is executed in order to identify certain categories of vulnerabilities, bad practices, or fragile structures that could compromise system security.
=== 1.2 Pedagogical positioning of the workshop

From a pedagogical standpoint, this workshop marks a shift in the learner's approach. In workshop 1, the main focus was on building a clean, organized, coherent, and testable project. In workshop 2, the goal is no longer simply to produce code, but to read code as a space of risk, understand its weaknesses, interpret the alerts raised by analysis tools, and then correct the problems in a reasoned manner.
This development is essential in a DevSecOps curriculum. A student might know how to develop a functional application without necessarily being able to identify when input validation is insufficient, when a business error is reporting too much information,

// PDF page 3; printed page 2
when an outdated component introduces a risk, or when a code structure enables certain undesirable behaviors. Workshop 2 aims precisely to develop this ability to critically read code, not simply as technical text, but as a potential source of vulnerabilities.
The educational role of SAST should therefore not be reduced to the mere use of a tool. The goal is not for the student to passively launch a scan and collect a report. The goal is for them to learn to understand the meaning of the alerts, to distinguish truly important vulnerabilities from secondary or debatable alerts, to connect the analysis results to the theoretical concepts of the course, and then to produce justified corrections consistent with the DigiBank architecture.
=== 1.3 Purpose of workshop 2

The purpose of workshop 2 is to conduct a complete static security analysis of the initial version of DigiBank, and then to correct the code and application configuration vulnerabilities that fall within the scope of SAST covered in the course.
In other words, the expected solution at the end of this workshop is not a new, different application, but a hardened, better controlled and technically safer version of the application built in workshop 1. This corrected version must maintain its good functional operation while reducing weaknesses detectable by reading the code, examining dependencies and analyzing application structures.
It is therefore important to understand that Workshop 2 is neither a purely theoretical audit nor a simple, opportunistic patching activity. It is a methodical process, rooted in DevSecOps principles, where code is examined early enough to prevent vulnerabilities from propagating through pipelines, containers, execution environments, or future iterations of the project.
=== 1.4 DevSecOps Workshop Logic

This workshop provides a very concrete illustration of the shift from late-stage security to built-in security. In a traditional approach, many security flaws are only detected during final audits, penetration tests, or after anomalies appear in testing or production environments. This makes remediation more costly, slower, and more disruptive, as the weaknesses are already embedded in the architecture, components, and business logic.

// PDF page 4; printed page 3
Conversely, the approach advocated here consists of analyzing the code as close as possible to its point of introduction. SAST enables precisely this early detection. By observing the source code, certain flows, constructs, missing validations, or sensitive configurations, the team can identify risk signals very early on and intervene before these problems become more difficult to correct.
In line with the course's logic, workshop 2 therefore embodies one of the first technical levers of the Shift Left. It shows that security does not begin at deployment, nor when an application is already exposed, but from the moment the classes, methods, controllers, services, configuration files and dependencies embedded in the project are read.
=== 1.5 Why DigiBank is a good support for a SAST workshop

The DigiBank project provides a particularly relevant framework for a static security analysis workshop, as it combines several characteristics typical of modern application systems. It handles potentially sensitive data, exposes REST APIs, implements business rules, relies on a relational database, integrates validations, depends on external libraries, and is already preparing for a form of industrialization via Docker and GitHub Actions.
These characteristics provide concrete material for static analysis. Even in a first educational version, such a project may present incomplete validations, overly detailed error messages, aging dependencies, overly visible secrets or test identifiers, insufficiently defined business rules, or structural choices that complicate access control or traceability of operations.
DigiBank's value also lies in its role as a central theme throughout the course. The vulnerabilities identified in Workshop 2 are not isolated from the rest of the course. They directly prepare the ground for Workshop 3, which focuses on DAST, and then Workshop 4, which addresses dependencies, containers, and delivery artifacts. The same project thus becomes a coherent field of observation, where security is progressively explored from several complementary perspectives.

=== 1.6 Definition of static analysis within the workshop

In this workshop, static analysis refers to the examination of DigiBank's source code, bytecode, or certain compilation artifacts without actually running the application, with the aim of identifying potential vulnerabilities or code structures deemed risky. SAST therefore seeks to identify what, in the way the software is written and organized, could constitute a security weakness, regardless of whether the application appears to function correctly.
This distinction is important because an application can be fully compilable, pass its business tests, and produce the expected results while still containing significant weaknesses. SAST therefore doesn't simply verify that the code "works." It seeks to determine whether this code unnecessarily introduces risks related to data validation, application flows, error handling, dependencies, the handling of sensitive information, or certain coding practices.
In workshop 2, this analysis will rely on both automated tools and a reasoned reading of the project. The student's work should never be limited to simply copying the results of a scan. They must understand the logic behind the identified vulnerabilities, place them within the context of DigiBank, and assess their likely impact on the application's security.
=== 1.7 General objective of the workshop

The overall objective of workshop 2 is to detect, analyze, prioritize and correct security vulnerabilities identifiable by static analysis in the DigiBank project, based on the SAST concepts studied in the course and on a DevSecOps approach oriented towards early prevention.
This overall objective involves four complementary dimensions. First, the student must know how to execute or utilize static analysis mechanisms. Second, they must be able to correctly interpret the results obtained. They must also produce relevant corrections without degrading the architecture or breaking the application's functional behavior. Finally, they must be able to justify the remediations performed based on clear security reasoning.
The workshop therefore does not only aim to raise alerts. It aims to transform these alerts into understanding, and then this understanding into concrete improvements to the code and configuration of the project.

=== 1.8 Specific Objectives

At the end of this workshop, the student should be able to:
* A2.1: Explain the role of SAST in a DevSecOps approach and link it to the Shift Left principle
* A2.2: Analyze DigiBank's source code from a security perspective
* A2.3: Identify the main categories of static vulnerabilities present in the project
* A2.4: Use tools such as SonarQube, OWASP Dependency-Check, and other static quality mechanisms to support your diagnosis

* A2.6: Correct the vulnerabilities detected in the code and in certain application configurations
* A2.7: Justify the remediation measures implemented from a technical and safety perspective.
* A2.8: Deliver a more robust version of DigiBank, ready to be subsequently submitted to the dynamic tests of workshop 3.
=== 1.9 Scope of the analysis in workshop 2

The scope of this workshop covers all vulnerabilities or weaknesses that can reasonably be identified without actively running the application. This includes the Java code of business modules, REST controllers, services, entities, DTOs, exceptions, validations, application configuration files, certain Maven dependency definitions, and build artifacts directly related to the project.
However, this workshop does not yet cover observing the application's actual behavior in operation, manipulating sessions through running HTTP requests, or analyzing dynamic responses from outside the application. These aspects fall under the DAST (Dynamic Application Support Team) and will be addressed in the following workshop.
This distinction is pedagogically important. It avoids confusing two complementary approaches: workshop 2 examines the software's internal structure, while workshop 3 will observe its external behavior. The DigiBank project will thus serve successively as a case

study for internal and then external analysis, reinforcing the overall coherence of the learning path.
=== 1.10 Types of vulnerabilities targeted

Within the DigiBank framework, the vulnerabilities or weaknesses sought through static analysis may include:
* Insufficient validation of user input
* Code structures that can facilitate certain injections or unsafe uses
* Overly revealing error messages or exceptions
* Secrets or identifiers visible in the configuration
* Outdated or known risky dependencies
* Fragile coding practices from a security standpoint
* Insufficient access controls when they already appear in the code structure or in the endpoint logic.
* Architectural or configuration choices that complicate risk reduction in a later phase.
It's important to note that some of these vulnerabilities don't necessarily mean that an exploit has already been proven. The role of SAST is precisely to flag potential weaknesses or concerning code patterns before they are tested through execution or an actual attack.
=== 1.11 Tools to use

The tools selected for the workshop cover development, static analysis, dependency checking, test quality, and pipeline automation. They should be presented as complementary instruments, each intervening at a specific level of the code security chain.
* IntelliJ IDEA: is used to open, read, modify and run the DigiBank project. It is the student's main working environment.
* JDK Java: allows you to compile and run the project. It forms the technical basis of the Java environment.
* Maven: manages dependencies, compilation, testing, and analysis plugins. It also serves as an entry point for running SAST checks.

// PDF page 8; printed page 7
* Spring Boot: provides the application framework for the analyzed project. It allows for an understanding of the actual organization of the source code under examination.
* SonarQube: analyzes code quality and flags security, maintainability, and robustness issues. It is the primary static analysis tool in the shop floor.
* OWASP Dependency-Check: checks project dependencies to identify libraries with known vulnerabilities.
* PITest: evaluates the robustness of tests by measuring their ability to detect artificial code modifications. It helps to judge the true quality of test coverage.
* JUnit 5: allows you to run or complete unit tests after correction. It is used to verify that the remediations have not broken the expected behavior.
* Git: allows you to track changes made to the code and keep a clear record of security fixes.
* GitHub: hosts the project repository and centralizes the analyzed code. It also serves as a platform for automation.
* GitHub Actions: automates compilation, testing, and analysis checks in the CI/CD pipeline. It shows how to integrate SAST into the development workflow.
=== 1.12 Expected result at the end of part 1

At the end of this first part, the student should have understood why workshop 2 exists, what a static security analysis really is, how it extends the DevSecOps logic studied in the course, and why DigiBank is a relevant field for this practical application.
He must also be able to explain:
* Why does SAST intervene before the application is executed?
* How does it embody the principle of Shift Left?
* What categories of vulnerabilities can be identified in the source code?
* Why the human interpretation of the results is as important as the tool itself
* And how this workshop logically prepares the future steps of the journey, in particular the DAST applied to the corrected version of DigiBank.
The next part can then move into the operational work itself: preparation of the analysis environment, choice of tools, execution of the first static checks, observation of the results and organization of the remediation.

== Part 2: Practical Preparation of DigiBank's SAST Environment

In this second part of Workshop 2, the goal is not yet to fix DigiBank's vulnerabilities, but to set up a reliable, reproducible, and consistent analysis environment. This step is crucial because a serious SAST workshop doesn't begin with blindly running tools, but with rigorous preparation of the project, Maven plugins, scanners, reports, and the pipeline that will then be used to automate the evaluation of code quality and security.
In keeping with the spirit of the course, this phase embodies the Shift Left principle: security checks should not be postponed until the end of the cycle, but integrated into the regular practices of building, testing, and reviewing code. SonarQube, OWASP Dependency-Check, PITest, and GitHub Actions are therefore not presented here as isolated tools, but as components of an initial static control chain applied to the DigiBank project.
=== 2.1 Role of this phase

Before launching any analysis, the student must start with a functional version of DigiBank, as built in Lab 1, including its Maven architecture, modules, dependencies, unit tests, and Spring Boot entry point. The Lab 1 PDF clearly demonstrates that DigiBank was designed from the outset to prepare for subsequent workshops, notably through the early integration of tests, API documentation, and automation tools such as Docker and GitHub Actions.
This section therefore has a dual purpose. On the one hand, it restores the project to a clean state before analysis; on the other hand, it installs the building blocks of static analysis which will then be used to identify flaws in the code, dependencies and the robustness of the tests.

=== 3.1 Role of this phase in the workshop

At this stage of workshop 2, the student has a rebuilt DigiBank project, equipped for static analysis and accompanied by tools capable of generating alerts, metrics, and reports. However, the pedagogical approach of this phase is not to mechanically copy the results of SonarQube, OWASP Dependency-Check, or PITest. Rather, it focuses on learning to interpret DigiBank as a risk environment, identifying weaknesses within its structure that make the application more susceptible to certain vulnerabilities, and then understanding why these weaknesses must be addressed.
This third part therefore constitutes the intellectual core of workshop 2. It is here that the student moves from technical instrumentation to security interpretation. After preparing the SAST environment, they must now examine the Java code, DTOs, services, controllers, exceptions, API responses, and configuration files in order to identify the main categories of static vulnerabilities targeted by the course.
The DigiBank project is particularly well-suited to this stage, as its first functional version was intentionally built as a clean, but not yet hardened, educational foundation. This means that the application works, compiles, exposes its APIs, and passes its main tests, while still containing a set of realistic weaknesses: insufficiently strict validations, overly verbose error messages, excessive exposure of certain data, secrets visible in the configuration, dependencies to monitor, and business logic that is sometimes insufficiently defined.
=== 3.2 General logic for identifying vulnerabilities

In a SAST workshop, not all vulnerabilities appear in the same form. Some are directly visible in the code, for example, a password written in plain text in an
data. Others are more subtle: weak validation, an insufficiently controlled critical business operation, a call structure that makes access controls difficult to implement, or a service that reveals exploitable information through its error messages.

----
application.yml file, an overly descriptive exception, or an output DTO exposing sensitive

For this reason, identifying vulnerabilities in DigiBank must follow a structured method. Students should not simply ask, “Is there a bug?” but rather: what data enters the system, how is it validated, what information is extracted, what business assumptions are implicit, what messages are exposed, what external components are used, and which parts of the system would be easy or difficult to further secure in subsequent workshops. This approach to analyzing the project corresponds exactly to the definition of static analysis given in Part 1 of Lab 2.
In this section, the analysis will be conducted module by module, in order to adhere to the DigiBank vertical architecture established in Lab 1. The common module will be examined for its exception handling and API response mechanisms. The customer-module, account-module, and transfer-module modules will be analyzed in terms of validations, data exposure, business rules, and error messages. Finally, the digibank-web module and the Maven files will be examined for configuration weaknesses and dependencies.
=== 3.3 Types of vulnerabilities actually searched for in DigiBank

In this version of DigiBank, the static vulnerabilities to identify fall into several categories consistent with the course material. The first concerns the validation of incoming data. Validation that is present but too permissive only provides superficial security. The second concerns error messages and exceptions. A banking application should not reveal too much information to a customer or a potential attacker about the existence of a resource, the status of an account, or the application's structure.
The third category encompasses the exposure of sensitive data in output DTOs or API responses. The fourth concerns secrets, credentials, and configuration parameters visible in versioned files. The fifth relates to dependencies and external components, which can introduce known vulnerabilities regardless of the quality of the internal code. Finally, a sixth category addresses the fragility of business rules, particularly in critical areas such as account creation and transfer execution.
The student must therefore be able to distinguish between a directly exploitable vulnerability and a structural signal of fragility. This distinction is important. SAST does not always prove the actual exploitation of a flaw, but it does indicate points where the risk is more likely, where the attack surface is expanded, or where future remediation will be more difficult if nothing is fixed now.

== Part 4: Detailed remediation of identified vulnerabilities

=== 4.1 Role of this phase

At this stage of Workshop 2, DigiBank has already been instrumented for static analysis, the monitoring tools have been configured, and the initial results from SonarQube, OWASP Dependency-Check, and PITest have revealed several categories of weaknesses. The objective is no longer simply to observe the alerts, but to move on to the most important work of the workshop: the reasoned remediation of the vulnerabilities and weaknesses detected in the source code and in certain project configurations.
This phase is central to the DevSecOps approach of the course. An alert only has educational value if it leads to an understanding of the risk, an appropriate remediation, and a clear verification of the resulting improvement. In DigiBank, this involves reworking certain classes, YAML files, and some Maven dependencies to transform a purely functional foundation into a more robust, better-controlled one that is more compatible with future DAST frameworks, containers, and security pipelines.
Remediation should never be approached as a mechanical series of patches. Each fix must remain consistent with the project's modular architecture, not break the expected

=== 5.1 Role of final validation in workshop 2

The final validation process confirms that the remediation implemented was not limited to a local or opportunistic fix, but that it effectively improved the overall security of the DigiBank project. From a pedagogical perspective, this step allows for a shift from a one-off fix approach to a technical mastery approach. Fixing a vulnerability is not simply a matter of modifying a few lines of code; it is demonstrating that the identified weakness has been understood, properly addressed, re-tested, and then integrated into a broader quality assurance process.
This phase is also important because a patch can introduce new side effects. Stricter input validation, for example, can break a previously tolerated business use case. === 5.2 What needs to be checked after remediation

Following the correction phase, several aspects must be explicitly rechecked. The first concerns the project's technical stability. DigiBank must still compile cleanly, its Maven modules must remain consistent, and existing tests must continue to run without unjustified regressions. The second dimension concerns the results of the SAST tools themselves. Alerts deemed critical or relevant in parts 3 and 4 must decrease, disappear, or be reclassified after remediation. This ability to justify actions is an integral part of the objectives of Workshop 2.

=== 5.5 Capitalization and traceability of corrections

The end of workshop 2 must also include a knowledge-sharing component. In a DevSecOps approach, it's not enough to simply fix things; you need to keep a clear record of what has been fixed, what remains to be observed, and the reasons behind the decisions made. Workshop 2 already highlights the importance of Git, Maven, and GitHub Actions in ensuring the reproducibility and traceability of changes applied to the project.
This knowledge sharing can take several complementary forms. First, Git commits must reflect understandable remediation intentions, not simply opaque changes. Second, the workshop report or associated technical note must explicitly state the identified vulnerabilities, their criticality level, the actions taken, and the results obtained after correction. Finally, when an alert is retained without immediate correction, this must be documented with a reasoned explanation, for example, due to a false positive, a transitive dependency that is difficult to replace at this stage, or a deliberate educational decision.
This traceability has a strong educational value. It teaches the student that professional security depends as much on the quality of reasoning and documentation as on the writing of the correction itself.
