= Digi Bank Microservices

This directory contains the complete Workshop 4 implementation for this
branch. The previous monolith implementation is kept on `main`.

== Service Boundaries

* `customer-service` -- customer identity and contact data
* `account-service` -- account lifecycle and status
* `transaction-service` -- financial operations and coordination
* `compliance-service` -- compliance decisions
* `notification-service` -- notification side effects
* `api-gateway` -- single client entry point
* `discovery-server` -- service registry boundary
* `config-server` -- centralized configuration boundary

== Validation Commands

Run the commands from this directory. The Makefile keeps the instructor
workflow short and consistent.

[source,shell]
----
make build
make image-build
make up
make status
make smoke
make validate-stack
make newman-scan
make zap-scan
make down
----

For focused work, use `make test`, `make logs`, or `make restart`. Use
`make clean` only when the database volumes should also be removed.

`make validate-stack` confirms every expected container is running. `make smoke`
waits for the gateway, discovery, config, and business endpoints before the
black-box Newman and ZAP checks are started.

== Request and Configuration Flow

Clients call `api-gateway` on port 8080. The gateway forwards customer,
account, transaction, and compliance requests to the corresponding service.
Each business service owns one PostgreSQL database and exposes only its own
REST resources. The transaction service calls account and notification through
explicit HTTP clients.

The `discovery-server` provides a lightweight registry at `/registry`. The
`config-server` provides service-specific configuration at `/config/{service}`.
Both boundaries are intentionally small for the workshop; they are not claimed
to be Eureka or Spring Cloud Config implementations.

== Distributed Patterns

* **CQRS:** transaction writes are handled by `TransactionService`, while
  reads are handled by `TransactionQueryService`.
* **Circuit Breaker:** notification calls use a bounded failure threshold and
  reset timeout so notification failure does not block the transaction flow.
* **Transfer Saga:** transaction processing coordinates account update,
  transaction persistence, notification, and account compensation steps.
* **Synchronous calls:** the implementation uses REST calls rather than adding
  a message broker.

== Database-per-Service

Compose provisions independent PostgreSQL databases for customer, account,
transaction, and compliance. Each persistence service owns its Flyway
migrations and validates its entity model with Hibernate `ddl-auto: validate`.
No service directly reads another service's database.

== Educational Boundaries

This version is deliberately scoped for the workshop. Discovery and
configuration are lightweight HTTP services, calls are synchronous, and the
system runs on one Docker Compose host. Production adoption would normally add
authenticated registration, external configuration storage, tracing, secrets
management, and a deployment platform.
